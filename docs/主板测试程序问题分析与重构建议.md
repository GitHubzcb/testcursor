# 主板（BLA）老化后测试程序 — 死机 / 数据传输异常 / 误判不合格 问题分析与重构建议

> 分析对象：MainBoardAfterAging.cpp/.h、BLACommunicate.cpp/.h、SerialPort.cpp/.h、
> pc_m2_protocol.c/.h、define.h、ElectrosurgicalAnalyzer.cpp/.h、PowerStation.cpp/.h、
> OscilloscopeCommunication.cpp/.h、CSpreadSheet.cpp/.h
>
> 症状：标定电流电压、低档/高档射频测试、阻抗测试、刺激输出各环节均可能出现
> ① 死机（界面卡死/程序崩溃）② 数据传输异常 ③ 主板液晶屏数据合格、但工装软件未收到最新数据而显示不合格。

---

## 一、结论摘要

这三类故障不是某一处孤立 bug，而是由**同一组结构性缺陷**在不同测试项上随机表现出来的，所以"从标定到刺激输出都有可能出现"。核心缺陷按影响排序：

| # | 缺陷 | 直接后果 |
|---|------|---------|
| 1 | 采集工作线程直接操作 MFC 控件（`UpdateData`、`GetCurSel`、`SetText`），UI 线程又大量 `Sleep()` | 跨线程 SendMessage 互相等待 → **界面卡死（死机）**、MFC 句柄映射断言崩溃 |
| 2 | 两个线程（状态轮询线程 + UI 按钮）**并发写同一串口**，且共用全局发送缓冲 `dat[2100]/send_len` 无任何互斥 | 发送帧交织/被覆盖 → MCU 收到坏帧 → **数据传输异常** |
| 3 | 串口接收：粘包重组后**校验的是 `sticky_buf`，解析的却是 `pBuf`**；overlapped 读未取 `GetOverlappedResult`；每次读写泄漏一个 Event 句柄 | 分包时解析垃圾数据、丢包；长时间运行句柄耗尽 → **数据异常 + 死机** |
| 4 | `WriteComm` 返回值语义反转（`length==0` 当成功），`curPage` 只在"失败"时更新；所有 `Get*` 靠 `curPage` 门禁 | 页面状态与 MCU 实际不同步 → 新数据被拒收 → **软件停留在旧值/不合格** |
| 5 | `pc_test_status` 大结构体接收线程 `memcpy` 覆写、判定线程同时读，无锁 | 撕裂读 → 偶发错误值 → **随机误判不合格** |
| 6 | 判定失败时沿用上一次残留值继续判定并写 Excel，无"数据已过期"标记 | 通讯一旦中断，**界面/Excel 显示的是旧的不合格值**，而液晶屏是实时的 → 症状③ |
| 7 | 多处缓冲区越界（`data[250]={0}`、`pComName[10][5]`、`sprintf_s` 长度谎报、`chname[6]`）、`m_ExitBlaThreadEvent` 从未创建就使用、`TerminateThread` 强杀线程 | 未定义行为 → **随机崩溃（死机）** |

**是否需要重构：需要。**"止血式"修 bug 可以显著降低故障率（见第五节 P0 清单），但通讯层（串口收发、协议解析、设备数据快照）和测试流程控制（按钮文本 + 定时器驱动的隐式状态机）必须重构，否则同类问题会不断复发。建议按第六节的三阶段方案执行。

## 三、死机类问题根因分析

### 3.1 工作线程直接操作 UI（首要死机原因）

采集线程 `RunDataCollection` → `ProcessTestData` → `GetShow7EleSurAnaBlaValue` 等函数在**非 UI 线程**里执行了：

- `UpdateData(FALSE)`（MainBoardAfterAging.cpp 第 2348 行，KingPo 分支）——MFC 明确禁止跨线程调用，窗口句柄映射是线程私有的，轻则断言崩溃，重则内存损坏；
- `m_eleType.GetCurSel()`（第 2335 行）、部分 `Get*` 里的 `m_UIxx.SetText(...)`——底层是 **SendMessage，跨线程时会阻塞直到 UI 线程处理消息**。

而 UI 线程在按钮处理函数和 `OnTimer` 里大量 `Sleep`（全文件 165 处 `Sleep`，含 `OnTimer` case 2 中的 `Sleep(3000)`）。时序一旦凑成：

```
UI 线程：  按钮处理中 Sleep(3000) / 等待 StopDataCollection 的 WaitForSingleObject(3000)
采集线程： SendMessage(GetCurSel/SetText) → 等 UI 线程泵消息
```

即形成**双向等待，界面彻底冻结**——这就是操作者看到的"死机"，且发生在哪个测试项取决于当时 `m_curBlatestFun` 的值，与"每个测试项都可能死机"的现象完全吻合。

### 3.2 UI 线程长阻塞 + 定时器重入

- `OnTimer` case 2 里 `Sleep(3000)`（第 8079 行）：UI 线程直接冻结 3 秒；期间定时器消息继续排队，`Sleep` 结束后 `OnTimer` 立即重入，而流程状态是靠 `GetWindowText` 读按钮文字判断的，重入会把状态机打乱（按钮被重复"点击"）。
- 几乎所有按钮处理函数内都有 1~3 次 `Sleep(200~1000)` + 同步仪器 IO（VISA 每次 open/close 一个会话并夹带 4 次 `Sleep(50)`），单击一次按钮 UI 可冻结数秒。

### 3.3 句柄泄漏（长时间运行后死机/系统异常）

`CSerialPort::ReadComm/WriteComm` 每次调用都 `CreateEvent` 却**从不 `CloseHandle`**：

```133:138:/home/ubuntu/.cursor/projects/workspace/uploads/SerialPort_ff6f.cpp
	OVERLAPPED osRead;
	memset(&osRead,0,sizeof(OVERLAPPED));
	osRead.hEvent = CreateEvent(NULL,TRUE,FALSE,NULL);

	DWORD dwByteOfRead = 0;
	bReadStat = ReadFile(m_hCom, buf, dwBytesRead, &dwByteOfRead, &osRead);
```

接收线程 30ms 读一次 + 状态线程 350ms 写一次 + 电刀线程 300ms 读一次，**每小时泄漏约 13 万个内核句柄**。运行数小时后进程句柄数达到几十万，系统资源耗尽，表现为程序卡死、CreateEvent/CreateFile 失败、甚至整机变慢——典型的"跑久了就死机"。

### 3.4 线程与串口生命周期管理错误

1. **`m_ExitBlaThreadEvent` 从未创建**。构造函数只创建了 `m_hDeviceInfoEvent`（BLACommunicate.cpp 第 19 行），随后 `ResetEvent / SetEvent / WaitForSingleObject` 全部作用在**未初始化的野句柄**上。副作用有二：
   - `CommGetBlaStateThread` 中 `WaitForSingleObject(野句柄, 2000)` 立刻返回 `WAIT_FAILED`，循环变成 ~350ms 高频轮询（"碰巧"实现了轮询，但纯属未定义行为）；
   - 关串口时线程**永远收不到退出信号**。
2. `closeBlaCOM` 里 `WaitForSingleObject(hGetBlaStateThread, 0)` 等待 0ms，不等线程退出就 `CloseConnection()` 关闭串口句柄；接收线程 `ThreadMethodBla` 与状态线程仍在对**已关闭的句柄**执行 `ReadComm/WriteComm`，且 overlapped IO 挂起时 `CloseHandle(m_hCom)` 本身就是未定义行为 → 随机崩溃。
3. 每次 `openBlaCOM` 都 `CreateThread` 新的状态线程，旧线程未退出 → 反复开关串口后**多个轮询线程并存**，同时向串口发 `GetBlaStatue`，加剧发送帧交织（见 4.1）。
4. `StopDataCollection` 超时后 `TerminateThread`（第 700 行）：强杀持有 CRT/堆锁的线程会造成堆损坏、锁永久占用 → 之后任意 malloc/UI 调用死锁。
5. `~CMainBoardAfterAging` 对 `AfxBeginThread` 默认 auto-delete 的 `m_pBlaComThread` 做 `WaitForSingleObject(m_pBlaComThread->m_hThread, ...)`——线程结束后 CWinThread 对象已 delete，访问悬空指针。

### 3.5 缓冲区越界（随机崩溃）

- `data[250] = {0};`（BLACommunicate.cpp 第 9 行）：这不是初始化，是**对下标 250 的越界写**（数组大小 250，合法下标 0~249）。同类：`fEletrodeTemp[2] = { 0.0 };`、`pComName[10][5] = NULL;`。
- `GetUsbSn`：`sprintf_s(pszComName, 100, ...)` 但实参 `ch` 只有 `TCHAR[10]`，谎报缓冲区大小使 `sprintf_s` 的保护失效；`pComName` 每项仅 5 字符，**"COM10" 以上（5 字符 + 结尾符 = 6）必然溢出**——恰好工装机器插多个 USB 串口时 COM 号常常 ≥10，与"插拔设备后崩溃"高度相关。
- `OnUpdateComboBox`/`OnTimer(1)` 中 `TCHAR chname[6]`，combo 文本超过 5 字符即栈溢出。
- `ThreadMethodBla` 中 `data_lenth` 直接来自报文字节且**无上限校验**，`pBuf[data_lenth + 9]` 最大可读到 `pBuf[65544]`，远超 1024 的缓冲区；粘包分支 `memcpy(sticky_buf + sticky_first_packet_len, pBuf, nCount)` 也可越过 `sticky_buf[1024]`。

### 3.6 VISA 使用方式

电源台/示波器每一次读写都完整执行 `viOpenDefaultRM → viOpen → viWrite/viRead → viClose ×2`，采集线程 10ms 循环反复做，同时 UI 线程按钮处理里也在做——**两个线程并发地高频开关 VISA 会话**，NI-VISA 在这种用法下容易内部死锁或资源泄漏，也是卡死来源之一。

## 四、数据传输异常 & "液晶屏合格、软件显示不合格" 根因分析

### 4.1 双线程并发写串口 + 全局发送缓冲无锁（最主要的传输异常来源）

`Pc_Com_Pack` 把帧组装进**全局** `char dat[2100]` / `send_len`（pc_m2_protocol.c 第 4~5 行）。调用方有两个并发线程：

- 状态轮询线程：`GetBlaStatue()`（每 ~350ms）；
- UI 线程：`PCSetBlaPageDisPlay / SetStimParameter / BlaStartandStop / PCControlBlaKey ...`（每个按钮都发）。

没有任何互斥。两个线程一旦同时进入 `Pc_Com_Pack`+`WriteComm`，就会出现：
① 组包到一半被另一线程覆盖 → 发出混合帧；② 两次 `WriteComm` 字节流在驱动层交织。MCU 收到坏帧后不应答或应答错 → 上位机拿不到新状态。**这解释了为什么每个测试项都可能出现数据异常——所有命令共用这一个缓冲。**

### 4.2 `ReadComm` 本身不可靠

```147:159:/home/ubuntu/.cursor/projects/workspace/uploads/SerialPort_ff6f.cpp
	if(!bReadStat)
	{
		if(GetLastError() == ERROR_IO_PENDING)
		{
			WaitForSingleObject(osRead.hEvent, 2000);
			//			GetOverlappedResult(m_hCom, &osRead,  &dwByteOfRead, FALSE) ; 

		}
	}
	//	PurgeComm(...)

	buf[dwByteOfRead] = '\0';
	return dwByteOfRead;
```

- **`GetOverlappedResult` 被注释掉了**：IO 进入 pending 时 `dwByteOfRead` 仍为 0，等待完成后直接返回 0——**这批数据被无声丢弃**（数据其实已写入 buf，但调用方拿到长度 0 当没收到）。
- `ClearCommError` 的判断 `if (!ClearCommError(...) && dwErrorFlags > 0)`：`&&` 写反了逻辑（调用失败时 `dwErrorFlags` 未定义；调用成功有错误时反而不清理）。
- 按 `cbInQue` 读，天然会读到半包/一包半，把组包完整性完全押在下游的粘包逻辑上。

### 4.3 粘包重组的关键 bug：校验 A、解析 B

`ThreadMethodBla` 的续包分支（BLACommunicate.cpp 第 161~178 行）：

```161:174:/home/ubuntu/.cursor/projects/workspace/uploads/BLACommunicate_5cb2.cpp
				if (sticky_buf[data_lenth + 9] == (unsigned char)0xCC && sticky_buf[data_lenth + 10] == (unsigned char)0x33 && sticky_first_packet_len >= 5)
				{
					...
					flag = *(pBuf + 2);
					if (flag == pc_com_test_get_status)
					{
						bla_pc_test_get_status_unpack(pBuf + 5, &pc_test_status);
					}
```

完整性校验用的是拼好的 `sticky_buf`，**解析时却用了只含后半段数据的 `pBuf`**：`pBuf+2` 是后半段的第 3 个字节（根本不是命令字），`pBuf+5` 更不是负载起点。结果一：命令字对不上，**这一帧被静默丢掉**；结果二（更糟）：恰好对上 `0x20`，则把错位的字节流 `memcpy` 进 `pc_test_status`——**全是垃圾值**。

串口 115200bps 下一帧状态包（`t_pc_test_status` 200+ 字节）传输约 20ms，接收循环 30ms 读一次，**分两次到达是常态而不是异常**，所以这个 bug 是高频触发的。这正是"主板液晶屏（MCU 本地数据）合格、上位机收不到最新数据"的直接原因之一。

其他缺陷：只支持"两段拼接"，三段或缓冲区头部有残留字节（帧头不在 `pBuf[0]`）时整帧丢弃；`nCount >= 5` 才解析长度但**校验分支没有确认收满 `data_lenth+11` 字节**。

### 4.4 协议无校验能力

`crc32_get` 直接 `return 0`（pc_m2_protocol.c 第 17~24 行），发送方填 0、接收方不验——线路上任何误码都无法被发现，坏数据会被当好数据解析。医疗测试工装依赖这些数据做合格判定，**必须有真实 CRC**。

### 4.5 `WriteComm` 返回值语义反转，`curPage` 门禁失效

`PCSetBlaPageDisPlay`（BLACommunicate.cpp 第 273~283 行）：

```273:283:/home/ubuntu/.cursor/projects/workspace/uploads/BLACommunicate_5cb2.cpp
	    DWORD length = m_BlaSerialPort.WriteComm((BYTE*)dat, send_len);
		if (length == 0)
		{
			curPage = page;
			bRet = TRUE;
		}
		else
		{
			bRet = FALSE;
		}
```

`WriteComm` 返回写入字节数，0 才是失败——这里**把失败当成功**。而 overlapped 写常常先返回 pending（拿到 0），偶尔同步完成（拿到实际长度），于是 `curPage` 是否更新**取决于当次 IO 的竞态**。更严重的是所有 `GetEleStimulation* / GetRF* / GetCQM ...` 都用 `curPage != PC_TEST_xxx_PAGE` 做门禁：`curPage` 一旦与 MCU 实际页面失步，**接收线程明明收到了新数据，判定函数却全部 `return FALSE` 拒绝取用**——界面/判定停留在旧值。注意同文件里 `BlaStartandStop/GetBlaStatue` 用的又是相反的约定（`==0` 判失败），两套约定必有一套是错的。

`curPage` 本身也是"我以为的页面"：MCU 实际页面在 `pc_test_status.pageID` 里有回传，却没有被用来同步。

### 4.6 数据撕裂与"旧值判定"

- 接收线程 `bla_pc_test_get_status_unpack` 对 200+ 字节结构体整体 `memcpy`，同一时刻采集线程/UI 线程在读 `pc_test_status.com_m0_back.*` 的 float——**读到一半旧一半新**（撕裂读），float 偶发呈现极端值，造成随机的"超差不合格"。
- 所有 `GetShowXX` 在 `Get*` 返回 FALSE 时**不清空、不标记过期**，继续拿上一次的成员变量值 `Format` 显示并写入 `m_bMainBoardAferAgingQulityFlag` / Excel 结构。通讯一旦中断（4.1~4.5 任一原因），**界面和 Excel 就冻结在最后一次成功的数据上**——操作者看到液晶屏是好的、软件是"不合格"，即症状③。
- 附带：`GetShow7EleSurAnaBlaValue` 里 `m_str7EleSurAnaPRW.Format(...)` 之后再判断 `!= ""` 永远为真，这几个合格标志实际形同虚设。

### 4.7 电刀（ESU）应答时序错配

`getContIPV`：发 `READ:ALL?` 后仅 `Sleep(100)` 就去解析 `m_strContinueIPV`，而接收线程 300ms 才轮询一次串口——**拿到的几乎总是上一次的应答**（滞后一拍）；`bGetAll` 布尔标志跨线程无同步；应答分包时 `CString strResponse(pBuf)` 只取前半。切负载后第一次读数经常是旧阻抗下的功率值 → 低档/高档测试随机超差。

## 五、解决方法

### P0（止血，立即修，不改架构）

1. **禁止工作线程碰 UI**：删除 `GetShow7EleSurAnaBlaValue` 中的 `UpdateData(FALSE)`；`m_eleType.GetCurSel()` 的结果在按钮处理（UI 线程）时缓存到普通成员变量；所有 `SetText` 只留在 `OnUpdateTestData`（已有此机制，补齐漏网的即可）。
2. **修粘包解析**：校验与解析统一用 `sticky_buf`；给 `data_lenth` 加上限（`<= BUFFERSIZE - 11`）；确认 `收到字节数 >= data_lenth + 11` 才校验帧尾。正确做法是改成**环形缓冲 + 逐字节扫描帧头**的通用组包器（见下方示例）。
3. **串口发送互斥**：`Pc_Com_Pack + WriteComm` 合并为一个受 `CRITICAL_SECTION` 保护的 `SendFrame(flag, payload, len)`，`dat/send_len` 改为局部变量或类成员，彻底消灭全局缓冲。
4. **修 `ReadComm/WriteComm`**：恢复 `GetOverlappedResult`；`CloseHandle(osRead.hEvent)`（或把 Event 做成类成员复用）；`WriteComm` 单独用输出变量接收写入长度；统一"返回 0 = 失败"，并修正 `PCSetBlaPageDisPlay` 等处反转的判断。
5. **修 `m_ExitBlaThreadEvent`**：构造函数里 `CreateEvent`；`closeBlaCOM` 顺序改为 *SetEvent → WaitForSingleObject(线程, 合理超时) → 停接收线程 → CloseConnection*；`openBlaCOM` 前确保旧线程已退出，防止轮询线程堆积。
6. **修越界**：`data[250]={0}` → `memset(data, 0, sizeof(data))`；`pComName[10][5]` 扩为 `[10][8]` 并去掉 `pComName[10][5]=NULL`；`sprintf_s` 的 size 用 `_countof(ch)`；`chname[6]` 加长度截断。
7. **去掉 `TerminateThread`**；采集线程循环里所有阻塞 IO 加超时，保证 3 秒内能自然退出。
8. **数据加锁/快照**：`pc_test_status` 用已有的 `m_csDataLock`（或新建 `CRITICAL_SECTION`）保护——接收线程解析到临时结构后加锁整体赋值；读方加锁拷贝快照再判定。
9. **数据有效期**：接收线程每成功解析一帧记 `GetTickCount()`；`Get*` 增加"数据龄 > 1s 视为无效"的判断；`GetShowXX` 在无效时把显示置为 `"—"`/黄色"通讯中断"，**绝不用旧值参与合格判定**——从根上消除症状③的误判。

粘包组包器示例（替换 `ThreadMethodBla` 内的解析）：

```cpp
// 环形缓冲逐帧提取：帧 = AA 55 | flag | lenL lenH | payload | crc32 | CC 33
static int TryExtractFrame(std::vector<u8>& rx, u8* out, int outCap)
{
    while (true) {
        // 丢弃帧头前的噪声字节
        size_t i = 0;
        while (i + 1 < rx.size() && !(rx[i] == 0xAA && rx[i+1] == 0x55)) ++i;
        rx.erase(rx.begin(), rx.begin() + i);
        if (rx.size() < 11) return 0;                 // 不足最小帧长，等下次
        u16 len = rx[3] | (rx[4] << 8);
        if (len > 2048) { rx.erase(rx.begin(), rx.begin() + 2); continue; } // 假帧头
        size_t total = (size_t)len + 11;
        if (rx.size() < total) return 0;              // 帧未收全，等下次
        if (rx[total-2] == 0xCC && rx[total-1] == 0x33 /* && CRC 校验通过 */) {
            int n = min((int)total, outCap);
            memcpy(out, rx.data(), n);
            rx.erase(rx.begin(), rx.begin() + total);
            return n;                                  // 取到一帧
        }
        rx.erase(rx.begin(), rx.begin() + 2);          // 帧尾不符：跳过假帧头重扫
    }
}
```

### P1（短期优化）

10. **采集线程节流**：10ms 轮询毫无必要（BLA 状态 350ms 才更新一次），改为 200~500ms，或改成"收到新帧才处理"的事件驱动；`PostMessage(WM_UPDATE_TEST_DATA)` 仅在数据实际变化时发，消除消息风暴。
11. **UI 线程去 Sleep**：按钮处理里的 `Sleep + 仪器 IO` 序列移入工作线程（`BlaComThreadProc` 已示范此模式，推广即可），完成后 PostMessage 回 UI；`OnTimer` 里的 `Sleep(3000)` 改为多级定时器状态推进。
12. **VISA 会话复用**：连接时 `viOpen` 一次保存 session，测试期间复用，断开时才 `viClose`；给电源台/示波器各加一把锁，禁止两个线程并发访问同一仪器。
13. **实现真实 CRC32**，PC 与 MCU 两侧同时启用校验（可用协议帧内保留位做版本协商，分步上线）。
14. **电刀读数改为请求-应答匹配**：发查询前清空应答缓存并记序号，接收线程解析到完整一行（以 `\r` 结尾）才置有效标志，`getContIPV` 等待"本次"应答（带超时），拿不到就返回失败而不是解析旧字符串。
15. `curPage` 与 `pc_test_status.pageID` 对账：翻页命令发出后等待状态帧回传的 pageID 确认，未确认前 `Get*` 返回"未就绪"。
16. Excel 写入移出 UI 线程；写失败（文件被占用等）给出明确提示并支持重试，避免测试数据丢失。

## 六、是否需要重构？——需要，建议三阶段

**判断依据**：上面 P0 修完后程序能稳定不少，但以下结构性问题决定了同类 bug 会持续产生：

- 9000 行的 `MainBoardAfterAging.cpp` 单文件承载了 UI、流程控制、仪器驱动调用、合格判定、Excel 持久化五种职责；
- 测试流程的状态存在**按钮文字**里（`GetWindowText(str); if (str == "xx停止")...`），定时器互相触发按钮处理函数，任何文案改动或重入都会破坏流程；
- 每新增一个测试项，就要复制一套 `OnBnClickedButtonXX + GetShowXX + UpdateXXUI + 保存` 四件套（现存 20+ 套近似重复代码），出错面持续扩大。

### 阶段一：止血（不动架构）
完成第五节 P0 全部条目。这一步后，死机与"假不合格"的发生率应下降一个数量级，为重构争取稳定窗口。

### 阶段二：通讯层重构（核心）

按设备抽象出统一的通讯层，每台设备一个 IO 线程 + 命令队列，对外只暴露线程安全接口：

```
IDevice
 ├─ BlaDevice        : 串口 + 帧协议；内部单线程收发；
 │                     对外: SendCommand(cmd, timeout) / GetStatusSnapshot()
 │                     快照 = {t_pc_test_status 副本, 时间戳, 有效标志}
 ├─ EsuAnalyzer      : 串口 SCPI；请求-应答匹配（带超时/重试）
 ├─ PowerStation     : VISA session 常驻 + 互斥
 └─ Oscilloscope     : VISA session 常驻 + 互斥
```

要点：
- **一台设备只有一个线程碰它的句柄**，命令通过队列进入该线程，天然消除并发写串口问题；
- 所有查询返回**带时间戳的快照**，UI/判定层永远拿不到撕裂或过期数据；
- 协议组包/解析集中在一个模块，环形缓冲 + CRC，可单元测试（用录制的字节流回放验证粘包、半包、误码场景）。

### 阶段三：测试流程引擎化

- 用显式状态机/测试项表驱动替代"按钮文本 + 5 个定时器"：每个测试项定义为 `{准备动作, 采集函数, 判定规则(上下限), 结果字段}` 的数据表，流程引擎顺序执行并回报进度；
- 合格判定规则（现在硬编码散落在 20 多个函数里的上下限）收敛为配置表，与 Excel 列一一对应；
- UI 只负责展示与启停，`MainBoardAfterAging.cpp` 预计可缩减到 2000 行以内。

### 风险控制

- 阶段二/三改动面大，建议：先给现有程序加**通讯日志**（收发原始字节 + 时间戳落盘），既能验证 P0 修复效果，也为重构后的回归对比提供基线；
- MCU 侧协议（帧格式、`t_pc_test_status` 布局，`#pragma pack(1)` 已正确）不需要动，重构仅限上位机，CRC 启用需与固件协商。
